# Testing

```sh
uv run pytest
uv run ruff check .
uv run pyright
```

All three are expected to be clean after every change (`CLAUDE.md`: "After
each milestone: run the checks..."). As of the current milestone: 195 tests,
`pytest`/`pytest-asyncio`/`hypothesis`, `ruff`, `pyright` (standard mode) —
see [`PROGRESS.md`](../PROGRESS.md) for the count at any given milestone.

## Configuration

[`pyproject.toml`](../pyproject.toml):

- `asyncio_mode = "auto"` — async test functions run without an explicit
  `@pytest.mark.asyncio` decorator.
- `testpaths = ["tests"]`.
- Ruff: line length 100, target `py312`, rule sets `E, F, I, UP, B, ASYNC,
  RUF`.
- Pyright: standard mode, over `src` and `tests`.
- Dev dependency group adds `pytest`, `pytest-asyncio`, `hypothesis`,
  `ruff`, `pyright`, and `aiosqlite` (the SQLite async driver used only by
  storage tests, never in production — see below).

## Fixture-driven parser tests: no invented payloads

Every parser test that exercises a venue wire format runs against **real
captured payloads**, never hand-written JSON — this is a `CLAUDE.md` rule,
not just a preference: "Parser tests run against real captured payloads in
`tests/fixtures/<venue>/`, never invented ones." The reasoning is direct:
inventing a payload means testing an assumption about the venue's format,
not the format itself, and both venues have already been observed to
diverge from their own documentation (see `docs/venue-notes.md`) — a
hand-written fixture would just re-encode whatever the author assumed,
including any wrong assumption.

### Fixture inventory

`tests/fixtures/kalshi/`:

  [`scripts/capture_kalshi_ws.py`](../scripts/capture_kalshi_ws.py)): 1

  markets. Reused across `test_kalshi_ws.py`, `test_kalshi_adapter.py`,

  `delta_fp: "-35.32"` → YES ask at `10000 - 7500 = 2500` ticks, qty
  `-353200`) against an actual observed frame, not a hand-derived one.
- `rest_markets_open_limit5.json`, `rest_market_kxpresperson-28-tgab.json`,
  `rest_event_kxpresperson-28.json`, `rest_series_kxpresperson.json`,
  `rest_series_kxnflgame.json`, `rest_orderbook_kxwc-30-por.json`,
  `rest_events_pairs_subset.json` — live REST responses covering markets
  listing, single market/event/series lookups (including both
  `fee_type` variants — `quadratic` and `quadratic_with_maker_fees`), an
  orderbook with real fractional contract counts (`"15.17"`,
  `"4903190.79"` — the payload that proved `Qty` needed to be fixed-point,
  not integer contracts), and an events page used by the pair-matcher test.

`tests/fixtures/polymarket_us/`:

- `rest_markets_limit2.json`, `rest_book_tec-mlb-nlchamp-2026-09-27-nym.json`,
  `rest_events_active_subset.json`, `rest_events_pairs_subset.json` — live
  gateway responses covering market listing, a real order book (whole-number
  but fixed-point-parsed quantity strings), and events pages for discovery

Capturing new fixtures re-runs
[`scripts/capture_kalshi_ws.py`](../scripts/capture_kalshi_ws.py), which is
parameterized (`CAPTURE_OUT`, duration, top-N markets, minimum delta count,
`--require-side`) precisely so a rarer message shape (like the NO-side
delta above) can be captured into its own file without disturbing the
pinned primary capture that other tests depend on. It never prints key
material, even though it authenticates to capture.

## Property-based tests: `hypothesis`

Used where the domain has a large input space and the invariant is more
interesting than any specific example:

- `test_types.py` — round-trip and boundary properties of the
  ticks/`Qty` fixed-point conversions (`ticks_from_dollars` ↔
  `dollars_from_ticks`, etc.) and `complement()`.
- `test_book.py` — `Book`'s validity state machine: sequences of
  snapshot/level updates generated by hypothesis, checked against the
  validity invariants from `CLAUDE.md` (never crossed while valid, sticky
  structural invalidation, staleness clearing on a contiguous update, etc.)
  — this is the exhaustive coverage `Book` gets specifically because it was
  designed as a pure, I/O-free data structure for exactly this kind of
  testing (see [`data-model.md`](data-model.md#book-validity-and-the-update-state-machine)).
- `test_supervise.py` — backoff sequence properties (monotonic growth up to
  the cap, jitter bounds, reset behavior).

## Storage tests run against real SQLAlchemy models, real SQLite

`test_storage.py` and any test touching `PaperTradeRow`/`PairRow`/
`RawMessageRow` run the *actual* SQLAlchemy models (no mocking of the ORM
layer) against an in-memory SQLite database via `aiosqlite` — fast, no
Docker/Postgres dependency for the unit-test loop, and it catches real
issues in model definitions (column types, constraints) because it's a
real database round-trip, not a stub. The one accommodation for SQLite's
narrower type system is the `with_variant(Integer(), "sqlite")` on every
primary key (see [`data-model.md`](data-model.md#primary-key-portability-note)).
Migrations themselves are Postgres-only and are not exercised by this fast
suite — they're verified against a real Postgres instance manually / via
`arb doctor`'s migration-state check once Compose is up (see
[`ops.md`](ops.md#migrations)).

## UI server tests without a browser or network

The UI splits cleanly into a **tested Python backend** and an **untested
browser frontend** (see [what isn't automated](#what-isnt-automated-yet)),
and the split is worth keeping in mind when reading a UI bug report: routes,
payload shapes and framing are covered; anything that only exists once a DOM
renders is not.

`test_ui_server.py` (20 tests) builds the FastAPI app via `create_app(state)`
against a stub implementing the `UIState` protocol (see
[`ui.md`](ui.md#uistate-how-the-routes-stay-testable)) — every HTTP route
and the WebSocket wire protocol (`hello`/`book`/`delta`/`stats`/`arb`/
`paper` framing, the client-queue-overflow-drops-the-client behavior) is
exercised with FastAPI's `TestClient`, no real network socket, no database,
no live venue connection.

Since the frontend became a multi-page app, that suite also pins the route
behavior the client-side router depends on — this is the half of "deep links
work" that Python can actually assert:

- every path in `SPA_ROUTES` returns the shell document, and still returns the
  plain-text fallback when `static/index.html` is absent;
- `/market/<market_id>` returns the shell for an id that is *not* a known
  market and for ids needing escaping (`%20`, `%2F`), because the id is
  resolved in the browser, not at the route;
- `/api/*`, `/metrics` and `/static/*` are not shadowed by any of the above —
  the regression guard against someone "simplifying" the enumerated routes
  into a catch-all;
- an unknown path (`/nope`, `/arb/deeper`, `/api/nope`) is still a 404.

End-to-end verification against a real browser (headless Chrome over the
DevTools protocol) has been done manually at several milestones — see
`PROGRESS.md` for what was checked live, including that the single WebSocket
survives a full round trip through every page — but is not part of the
automated suite.

## Adapter and matcher tests

- `test_kalshi_adapter.py`, `test_kalshi_ws.py`, `test_kalshi_rest.py`,
  `test_kalshi_auth.py`, `test_kalshi_source.py`, `test_kalshi_detail.py` —
  cover [`venues/kalshi.md`](venues/kalshi.md)'s modules individually:
  signing (with throwaway generated keys, never real ones), WS parsing
  against captures, subscription-scoped gap detection, REST parsing against
  captures, the `EventSource` reconnect/resubscribe wiring, and the DES
  payload builder.
- `test_polymarket_us_rest.py`, `test_polymarket_us_source.py` — the
  Polymarket US equivalents: REST parsing against captures, and the
  rate-limited poller's behavior on 200/429/error responses (via an
  injectable `fetch` callable, so the 5-token-bucket-then-429 behavior can
  be tested deterministically without hitting the real gateway).
- `test_pairs.py` — the matcher's scoring and blocking, on event fixtures
  taken verbatim from both venues' captured universes (not synthetic
  titles), plus the storage layer's upsert/decide semantics.
- `test_fees_edge.py` — fee formulas against each venue's documented
  worked examples, and the depth-aware edge walk against hand-constructed
  (not fixture-derived — these are pure math, no wire format involved)
  ladder scenarios covering partial fills, fee-exhaustion stopping, and
  both-direction selection.
- `test_arbmon.py`, `test_paper.py`, `test_replay.py` — the monitor's
  quoting, the paper trader's limit/scaling logic, and end-to-end replay
  behavior against a small recorded-run fixture built from the same real
  captures.

## What isn't automated (yet)

- Real venue connectivity (both WS and REST) is checked live and by hand at
  milestone boundaries and recorded in `PROGRESS.md`/`docs/venue-notes.md`,
  not re-verified by CI on every change — there is no CI job that hits
  production Kalshi/Polymarket US endpoints.
- Grafana dashboard correctness (panel queries actually rendering sensible
  data) is checked by hand against a live Compose stack, not asserted in a
  test.
- Browser-level UI behavior (select-to-copy, page navigation and the
  History-API router, keyboard shortcuts) has been verified manually over the
  Chrome DevTools protocol at several milestones (see `PROGRESS.md`) but has
  no automated browser test suite.
- **The browser frontend has no JS tests.** There is no JS harness in the repo
  — no `package.json`, no vitest/jest — so the only check `src/arb/ui/static/js/`
  gets is `node --check` per file, which finds syntax errors and nothing else.
  Reverting either M17 sparkline fix would still pass every check in the repo.

  What the multi-page restructure changed is *reachability*, not coverage.
  The pre-multipage `static/app.js` (deleted; it lives in git history) was one
  IIFE with no exports, so a harness had nothing to import. Today the frontend
  is ES modules that do export: `js/core/*` exports named functions and every
  `js/pages/*.js` default-exports its page object. The cheap first target is
  [`js/core/format.js`](../src/arb/ui/static/js/core/format.js) — it imports
  nothing and touches no DOM, and it is where the numbers come from (tick→cent
  and fixed-point quantity formatting, `percentile`, the duration/age
  formatters), exactly the kind of arithmetic that breaks silently and still
  reads plausibly. `js/core/state.js`'s selection helpers are nearly as easy
  (one `requestAnimationFrame` and one `document.body` touch away).

  The rest still needs a real browser, and some of it is not even importable
  in isolation: the sparkline geometry is a closure inside
  `pages/monitor.js`'s `drawSpark`, the router's path compiler and matcher are
  module-private and `register()` reaches for `document`, and mount/unmount,
  key routing and select-to-copy are DOM behavior by definition. Worth a
  harness — starting with `core/format.js` — if the frontend grows more logic
  than rendering.
